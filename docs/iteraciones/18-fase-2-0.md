## 1. Objetivo

Preparar la Fase 2 sin empezar features: fijar contratos, decisiones de
almacenamiento, DTOs y fixtures, y separar el código en módulos para que dos
builders puedan trabajar en paralelo sin conflictos.

La Fase 2.0 **no añade funciones de producto**. Su salida es documentación
normativa y un refactor sin cambio de comportamiento.

## 2. Decisiones iniciales

Estas decisiones se registran antes de escribir código. Pueden revisarse en la
revisión de 2.0, pero no se cambian a mitad de un bloque.

### 2.1 Manuscrito y «partes»

Se mantiene la estructura v1 `libro → capítulo → escena` durante la Fase 2.0.
«Partes» no se simula con campos ambiguos: se diseñará como una migración
dedicada en una fase posterior, con compatibilidad de lectura v1 y una prueba
de ida y vuelta. Hasta entonces, la UI no mostrará un nivel de partes que el
motor no pueda validar.

### 2.2 Comentarios

- El ancla vive en el Markdown.
- La sintaxis v2 añade un ULID al comentario:
  `[[comentario:ULID|texto del comentario|texto marcado]]`.
- El hilo, autor, estado, timestamps y respuestas viven en
  `.escritor/comentarios/<ULID>.json`, no en el Markdown.
- Los comentarios v1 de dos campos se conservan como legado de solo lectura; no
  se reescriben ni se pierden.
- El backup del proyecto incluye `.escritor/comentarios/`.
- Los comentarios huérfanos se marcan cuando el ancla desaparece; no se borran
  automáticamente.

### 2.3 Metas y temporizador

- Metas y sesiones son locales al proyecto: `.escritor/metas/` y
  `.escritor/sesiones/`.
- La racha diaria se agrega desde las sesiones de los proyectos abiertos.
- No hay cuenta, servidor ni sincronización.
- El backup incluye ambos directorios.

### 2.4 Planificación

- Personajes, tramas, lugares, cronología y objetos siguen siendo notas
  Markdown en `notas/`.
- El Plot Grid y el estado visual viven en
  `.escritor/planificacion/plot-grid.json`.
- Las @menciones usan ULID y se resuelven contra las notas; una referencia
  desconocida se muestra como tal, no se borra.
- Ideas es un cuaderno local dentro del proyecto; no hay tarjeta en el panel.

### 2.5 Plantillas

- Las plantillas son locales y viven en el directorio de datos de la app, no en
  el proyecto.
- Crear desde plantilla copia estructura y notas; no copia IDs ni historial.
- No hay biblioteca pública ni descarga.

### 2.6 Importación y exportación

- Prioridad: DOCX y Markdown primero; HTML y RTF después.
- Los parsers se ejecutan en local, con límites de tamaño y cuarentena.
- Todo DOCX/HTML/RTF malformado se rechaza sin tocar el proyecto.
- El backup y la importación de base de datos son parte del mismo contrato.

### 2.7 Windows

Sigue pendiente de máquina o runner CI. No se declara soporte hasta build,
instalador y pruebas reales.

## 3. Módulos objetivo

### Núcleo Rust

`crates/core/src/` se separa en módulos con responsabilidades acotadas:

```text
manuscript.rs    libros, capítulos, escenas, mover/duplicar/archivar
comments.rs      anclas, hilos, huérfanos
goals.rs         metas, sesiones, rachas
planning.rs      plot grid, referencias
templates.rs     plantillas locales
import.rs        DOCX/Markdown/HTML/RTF
export.rs        DOCX/Markdown/PDF
```

`project.rs` queda como fachada de transacciones y lock; no concentra las
reglas de cada feature.

### UI

`ui/src/` se separa en features con archivos propios:

```text
features/projects/       panel y tarjetas
features/manuscript/     árbol y operaciones
features/comments/       hilos, sticky notes, historial
features/planning/       plot grid, personajes, story notes
features/goals/          metas, rachas, temporizador
features/importexport/   diálogos y estados
features/templates/      plantillas e ideas
```

`App.tsx` queda como shell y composición. `styles.css` se divide por feature;
el shell conserva tokens y layout global.

## 6. Orden de trabajo

1. Escribir `esquema-v2.md` y los contratos de almacenamiento.
2. Añadir DTOs y fixtures v1/v2.
3. Separar el núcleo en módulos manteniendo los 94 tests.
4. Separar la UI en features manteniendo el comportamiento y el E2E.
5. Congelar 2.0 y revisar con el pipeline habitual.
6. Solo entonces abrir 2.1 (manuscrito) y 2.2 (comentarios).

## 7. Riesgos

- **Migración de comentarios:** el formato v1 no tiene ID. Mitigación: legado de
  solo lectura y no reescritura automática.
- **Modularización:** un refactor grande puede introducir regresiones.
  Mitigación: refactor sin cambio de comportamiento, tests actuales y E2E antes
  de tocar features.
- **Partes:** forzar un cuarto nivel ahora rompería proyectos v1. Mitigación:
  posponerlo a una migración dedicada.
- **Paralelismo:** sin módulos disjuntos, dos builders chocan. Mitigación:
  cerrar 2.0 antes de abrir 2.1/2.2.
- **Windows:** sin hardware/CI no se puede validar. Mitigación: preparar el
  runner durante la Fase 2, no declarar soporte.
